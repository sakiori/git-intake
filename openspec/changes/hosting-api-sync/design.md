## The merge request is the update

Until now an update published through a merge request stayed alive on the machine that opened it: the state kept the verified commit and every commit pushed since, `finish` was run again to catch the merge request up or to complete the update, and completion reconstructed from trees and parents whether what landed was the verified commit. That design had one reason: the tool could not see how the forge merges, so it verified locally and then checked after the fact that nothing else had landed. It had three costs. The update was tied to one clone, which a CI job does not keep. Any commit added to the merge request branch, including a fix, made the update fail. And the landing rules grew into the longest requirement of the specification.

With the forge's API the tool can see what it could not: whether a merge request is open, merged or closed, and whether the project merges only a tree a required pipeline tested. The guarantee then moves to where the merge happens. In merge-request mode the pipeline of the merge request verifies the update, the forge's settings make sure that the tested tree is the merged tree, and the tool refuses a project whose settings do not. The merge request itself becomes the update's state: `finish` pushes the branch, opens or updates the merge request and ends the local update; `sync` reads the merge request back from the forge, and so does a person running it on any clone.

What disappears with the local waiting step: the waiting state, the `pushed` list and `last_seen_head`, the landing judgement by trees, completion by a second `finish`, and the requirement to verify locally in merge-request mode. A local `verify` stays available, and push mode keeps requiring it, because there nothing else verifies the commit before it lands.

The local integration branch no longer moves when a merge request is merged. `start` and `sync` bring a strictly behind integration branch up to date, which covers the next update. In merge-request mode both refuse a local integration branch with commits the remote lacks, as `finish --no-publish` can leave: such commits would ride along in the next merge request unannounced.

The guarantee is the forge's, and so is its limit. People the forge lets bypass its rules, administrators on GitHub without enforcement for them or bypass actors of a ruleset, can merge anything, as they can push anything. The tool cannot see GitHub's bypass lists through the endpoints it reads and does not claim to control them.

## What the forge must guarantee

The guarantee needs two things: the merge cannot happen without a successful pipeline, and the tree that pipeline tested is the tree that lands. Squash and rebase merges are excluded independently, because they drop the merge commits whose trailers are the sync records.

**GitLab.** A successful pipeline is required by `only_allow_merge_if_pipeline_succeeds`, and a skipped pipeline must not count, so `allow_merge_on_skipped_pipeline` must be off. With the merge method *fast-forward* or *merge commit with semi-linear history*, GitLab merges only a source branch that contains the target branch, so the merged tree is the tree of the source branch's head, which the pipeline tested. With the plain *merge commit* method the merged tree is a new merge, and a merged results pipeline is not enough: GitLab checks that the pipeline ran for the merge request's head commit, not that the target branch is still where it was, so a merged results pipeline can be outdated when the merge happens.

Merge trains do not qualify with any method. With the plain merge commit method, whether the train lands the exact commit it tested could not be confirmed. With fast-forward or semi-linear history, the train's refs are rebased, and GitLab's rebase drops merge commits. The same rebase is the hazard of fast-forward and semi-linear history without trains: a source branch behind its target is made mergeable in GitLab's interface by *Rebase*, and since GitLab 19.2 can be rebased automatically before the merge. The tool keeps the branch mergeable itself, by catch-up merges, so it never needs a rebase. It requires automatic rebase to be off, counting the setting as off on instances that do not have it, and catches a rebase done by hand through the merge request's history (see *Rewritten branches*).

`squash_option` `always` squashes every merge request and is refused. `default_on` and `default_off` let the person merging tick squash, which the tool cannot prevent; it says so as a warning each time it pushes the update. The per-branch squash setting of GitLab Premium cannot be read through REST, only through an experimental GraphQL field, so the tool does not read it. A squash that happens anyway shows afterwards as a merge request merged without its history; `status` names it, and `sync` proposes the same targets again, naming it, since only a merge with its history records them.

Every field the tool reads on GitLab is visible to any token that can read the project. The merge train fields exist only on licensed tiers and count as off when absent.

**GitHub.** Required status checks must be on, must name at least one check, and must require the branch to be up to date before merging (strict); then GitHub merges a pull request only when its head contains the base branch and its checks passed on that head, so the merge commit's tree is the head's tree. Without strict, `pull_request` workflows test `refs/pull/<n>/merge` as it was when they started, which can be outdated. A merge queue tests the base with the pull requests ahead of it, but GitHub's documentation does not say whether it lands that tested commit or makes a new one, so a branch with a merge queue is refused, as GitLab's merge trains are. Merge commits must be allowed, and `required_linear_history` must not apply, since it forbids them. Squash and rebase merges that stay selectable produce the same warning as on GitLab, unless a ruleset's `allowed_merge_methods` limits the branch to merge commits.

The tool reads GitHub's settings from `GET /repos/{owner}/{repo}/rules/branches/{branch}`, which returns the rules of active repository and organisation rulesets to any token that can read the repository, and from the repository's `allow_merge_commit`, `allow_squash_merge` and `allow_rebase_merge`, which GitHub returns only to a token with push access; absent, they are unknown, not false. Classic branch protection is readable only with administration access. Whatever the token cannot read and the rules do not settle, the tool cannot confirm, and it refuses, naming the requirement and both ways out: express it as a ruleset, or give the token the access it lacks.

Settings are read before every push of an update branch, by `finish` and by `sync`, and by `doctor`. A project can change them at any time; checking them at the moment of publication is what the guarantee needs.

## Rewritten branches

A merge request branch that someone rebased or force-pushed no longer carries the update as the tool made it: a rebase on either forge drops the sync merges, and their trailers with them. Looking at the head alone catches the plain case, a head with no sync merge and no copy, but not a mix where port copies survive while follow merges vanish. The forges record the rewrite itself: GitHub's pull request timeline has a force-push event, and each push to a GitLab merge request makes a version whose head commit the API lists, so an earlier version's head that the current head does not contain, or that the clone cannot fetch, shows a rewrite. Comparing heads by ancestry, rather than the versions' commit lists, keeps a commit that reached the integration branch by another route from looking like a rewrite. `sync` refuses to act on an open merge request rewritten either way. A merged one counts as merged without its history, as a squash does, which is how the rewrite is still seen after a fast-forward merge of a rebased branch, when the integration branch does contain the merged head.

## The update line

Several rules need to know which commits are the update's: `env`, carrying on a merge request, and the check for a rewritten branch. "Every commit between the head and the base" is wrong for them, because a sync merge brings in the upstream's whole history, which may carry sync records of its own, as a stacked downstream branch does. The update line walks from the head along first parents, as the update branch grows, and crosses to the second parent only at a merge whose first parent the base already contains and that carries no sync record: a catch-up merge, or the merge a merged results pipeline tests. A merge the forge's update button makes has the branch's previous head as its first parent and stays on the line. Sync records and copies count only on that line, mirroring how the integration line treats the integration branch.

## Talking to the forge

The tool needs about a dozen requests per forge: find merge requests by source and target branch and state, open one, change its title and description, close it, list its commits and its history of pushes, read the project's merge settings, and on GitHub the branch rules. A `forge` module defines that interface once, with a GitLab and a GitHub implementation, and every command uses only the interface.

The HTTP client is `ureq`: synchronous, without an async runtime, with rustls, and it builds as a static musl binary like the rest of the tool. `reqwest` always brings tokio, even in blocking mode, and its default TLS backend needs a C toolchain for a static musl build. The `gitlab` crate defaults to reqwest's blocking client and follows GitLab's version monthly; `octocrab` is asynchronous only. For a dozen requests, a small module over `ureq` and `serde_json` is the smaller and steadier dependency. `ureq` honours `HTTPS_PROXY`, `ALL_PROXY` and `NO_PROXY`. It verifies certificates with the platform's verifier, which reads `SSL_CERT_FILE` and the system's trust store, because a self-managed GitLab behind a private certificate authority is common and a fixed root bundle would refuse it. Redirects to another host are followed without the token.

GitHub requests pin the API version `2022-11-28`. The newer `2026-03-10` drops `merge_commit_sha`, and GitHub Enterprise Server releases before 3.21 know only the older version. The tool does not need `merge_commit_sha`: whether a merge request landed its head is a git question, answered by ancestry against the fetched integration branch, which works the same on both forges.

## Finding the forge, its API and the token

The forge is that of the publish remote's fetch URL; further push URLs receive the branch as mirrors, as before, without merge requests. The publication setting is read from the configuration at the integration tip, never from an update's head, which carries content merged from upstreams: otherwise an upstream could point the token at a host of its choosing. For the same reason the `api` setting must name the remote's own host.

The forge kind comes from, in order: the setting `forge`; the remote's host, `gitlab.com`, `github.com` or a `ghe.com` subdomain; the CI environment, when the remote's host is that of `CI_SERVER_URL` in a GitLab job or of `GITHUB_SERVER_URL` in a GitHub Actions job. The API base comes from the setting `api`, else from `CI_API_V4_URL` or `GITHUB_API_URL` when the job's server is the remote's host, else `https://<host>/api/v4` for GitLab, `https://api.github.com` for github.com, `https://api.<host>` for `ghe.com` and `https://<host>/api/v3` for GitHub Enterprise Server. The project is the path of the remote's URL, without `.git` and credentials, and without the path prefix that the API base carries before `/api/v4` or `/api/v3`, which covers a GitLab installed under a relative URL root. An SSH host alias or an SSH URL of such an installation names neither the real host nor the root; the settings `forge` and `api` give them.

The token comes from the environment only, under the names the forges' own command-line tools use: `GITLAB_TOKEN` for GitLab, sent as `PRIVATE-TOKEN`; `GH_TOKEN`, then `GITHUB_TOKEN`, for github.com and `ghe.com`; `GH_ENTERPRISE_TOKEN`, then `GITHUB_ENTERPRISE_TOKEN`, for GitHub Enterprise Server, where a github.com token must not be sent, except in an Actions job of that server, whose `GITHUB_TOKEN` belongs to it. Reading git's credential helpers, as Git LFS does, was considered: it would spare a variable on a desktop, but a credential stored for pushing often lacks API scope, and a CI job sets variables anyway. The tool never prints a token.

The token must be able to open merge requests, and on GitHub the pull request's checks must start without a person approving them. GitLab's CI job token cannot open merge requests, and the pushes it may make when a project allows them start no pipeline. On GitHub, pushes made with Actions' `GITHUB_TOKEN` start no workflow, and pull requests it opens start their runs only after someone approves them, so unattended updates need a GitHub App token or a fine-grained token. The tool cannot tell these tokens apart; the README says which to use. Pushing goes through git with the remote's own configuration, as before: the tool does not put the API token into git's configuration.

## Code from upstreams in CI

An update brings upstream code into the repository, and its checks run that code: locally in `verify`, in CI in `sync`'s push mode or in the merge request's pipeline. That was true before this change; what changes is that it can now happen on a schedule, before a person has looked at the update. A pipeline of a merge request from a branch of the same repository gets that repository's non-protected CI variables on GitLab and its secrets on GitHub, and a root upstream that changes the CI definition changes the pipeline that tests it. In push mode, the job that runs the checks also holds the credentials it pushes with, typically in the clone's git configuration.

The tool does not pretend to fence this off: hiding its own token variables from the checks would not protect the push credentials beside them, and would break checks that use those variables for their own purposes. The tool makes the exposure visible: when an update changes the CI definition or the configured checks, `finish` and `sync` name the change in their output and in the merge request's description, since the pipeline that is supposed to verify the update then runs what the update brings. The README states the model: upstreams are code the repository chooses to run; keep deploy secrets in protected variables or environments that update branches cannot reach; on GitHub, a token without the Workflows permission cannot push an update that changes `.github/workflows`, which stops such an update for a person to publish by hand; and in push mode, give the job only the credential it pushes with. `SECURITY.md`, planned for the open-source release, carries the same model.

## Synchronising without local state

`sync` is what a scheduled CI job runs, and what a person runs to take over where a job stopped. Each run derives everything from the publish remote, its forge and the upstreams, and carries the update as far as it can:

1. With the update's merge request open, it brings it up to date: a catch-up merge onto the merge request's head when the integration branch moved past it, pushed without force, and the title and description rewritten. Otherwise it changes nothing. Upstreams that moved since the merge request was opened wait for the next update; a follow target stays fixed for the life of an update, as it always has.
2. Without one, it plans an update of every follow upstream that is behind, as `start` would with no upstream named. Port upstreams need a reviewed plan, and upstreams that cannot be fetched, have no release or were rewritten are left out and named, so that one broken source does not stop the others; the run then ends with a negative status for the job to show. When the newest closed merge request carried the same targets, it opens nothing: a person declined those targets, and the next update comes when an upstream moves on, or by hand with `start` and `finish`.
3. In push mode there is no merge request; `sync` starts, verifies and publishes in one run.

A conflict, in an upstream merge or a catch-up merge, stops `sync` exactly as it stops `start`, with the update in progress in the update worktree. In CI the job fails and the clone is discarded. A person then runs `sync` on their own clone, gets the same stop while nothing moved, resolves it, and runs `continue` and `finish`. That reuse is why the catch-up of an open merge request runs in a local update: `sync` takes the merge request's head as the update branch and recreates the update's state from it, the base, the upstreams it takes and their targets, before it merges. Any refusal on the way, such as a catch-up precondition, removes the update `sync` created, so that the next scheduled run meets the same situation and not an update in progress.

Recreating from history is possible because an update describes itself: the update's commits are those the head has and the base lacks, the base is where the head meets the integration branch, each follow upstream merge carries its sync record, each copy its copy trailers, and the port journal its decisions. What the history does not carry, the logs and the conflict list of earlier steps, `report` cannot show for a recreated update, and says so.

The update's branch can outlive its merge request. GitHub keeps the branch of a closed pull request and, unless the repository deletes head branches on merge, of a merged one; a job can be killed between pushing the branch and opening the merge request; an `abort --merge-request` can stop between closing and deleting. `sync` therefore treats a branch without an open merge request by what it holds: one at the head of a closed or merged merge request of the update, or contained in the integration branch, is deleted under a lease and the run goes on; one that holds an update no merge request carries is carried on and gets its merge request, unless it carries targets a person declined; anything else is refused, because the branch may be someone's work. Deletion always uses a lease on the commit read, so that a commit pushed in the meantime is never lost.

The declined-targets rule needs the targets of a closed merge request. Its commits are an unreliable source: GitHub lists at most 250 commits of a pull request, and a follow update lists every upstream commit it brings, so the sync merge itself is often cut off; GitLab deletes the reference to a closed merge request's head after two weeks. The description, which belongs to the tool, therefore ends with a block, hidden when rendered, that records each follow upstream's target. A description without a readable block, as one written by an earlier release or edited by hand, declines nothing: proposing an update again is the safe side of that mistake.

Two jobs running at once share one branch. The first push wins and the second is rejected as not a fast-forward, which `sync` reports as an error to run again. Opening a merge request for a branch that has one already is refused by both forges; `sync` reads the open one instead. A merge request merged or closed while `sync` catches it up is caught by reading its state again just before the push; one that changes in the instant between that read and the push leaves a branch that the push recreated, which the tool deletes while it is still at the pushed commit.

A merged merge request needs nothing: its update reached the integration branch, and the next plan starts from there. One merged without its history is named by `status`, and `sync` proposes the same targets again, naming it: the new merge request carries little more than the sync records, and merging it records them. Every retry waits for a person to merge it, so a project that squashes everything gets one open merge request, not a loop.

A squash commit's message can end with trailers copied from the update's merges, especially on GitHub, which joins the commit messages. A sync record therefore counts only on a merge commit whose second parent is its target, which every sync merge the tool makes is.

## The update's variables outside verify

`verify` describes an update to its checks through `GIT_INTAKE_*` variables. A merge request pipeline runs its own jobs, on a fresh clone with no update state, so `env` reads the same description from history. For a commit H and the integration branch's tip T, the base is the merge base of H and T: before any catch-up the integration tip the update started from, after one the tip it last caught up with, and for a merged results pipeline, whose commit is a merge of the update onto the target, that target commit, which is the base of the tree being tested. The update's upstreams and targets come from the sync records and copy trailers on the update line, their previous synced commits from the integration line at the base.

The port target needed one change for `verify` and `env` to agree. `verify` gave the newest commit of the plan, which can be a commit left `later`, and a plan leaves no trace in history. Both now give the newest commit the update takes or decides, which is what the update moves the upstream to in the journal.

`env -- <command>` runs the command with the variables and fails without running it when the variables cannot be read; `--dotenv` writes a file a GitLab dotenv report or GitHub's environment file takes. These are the forms the README recommends, because `eval "$(git intake env)"` loses `env`'s exit status and would run a check without its variables. A commit that is not an update gets none of them, so a check that falls back to its usual baseline outside an update keeps working in a pipeline that fetches the full history.

## Shallow repositories

Every command reads the integration line, and a shallow clone cuts it off: the last sync record of an upstream may lie below the shallow boundary, and the tool would plan from the wrong commit without noticing. CI systems clone shallow by default. Every command, `env` included, refuses in a shallow repository and names the way to fetch the full history; deepening the clone on its own would turn a reading command into a large fetch nobody asked for.

## Updates waiting from an earlier release

An update of format 4 or 5 waiting for its merge request has a local state this release no longer keeps. The first `finish` hands it over: it finds the merge request through the API, by its recorded number or else by branch, says whether it is open, merged or closed, records the resolutions of a catch-up step it may have stopped in, and removes the local worktree, state, branch and references, since the merge request carries the update from then on. Its branch may be `git-intake/update-<commit>`, the name format 4 used, so the update's merge request is found on either name. `abort --merge-request` withdraws it as any open one; `abort` only removes the local update. The state format stays 5: an update in progress before `finish` is recorded as before, and an earlier release of format 5 can carry on one started by this release, under its own rules.

## Withdrawing

`abort` keeps its meaning, removing the local update and nothing on the remote. Closing a merge request that a CI job opened, possibly while someone reviews it, is a different act, and it gets its own spelling: `abort --merge-request`. Running `abort` twice never escalates from the local update to the remote.

## Left out

- Requesting that the forge merge automatically when the pipeline passes. It is a policy of the project, not of the update, and forges offer it on the merge request.
- Port upstreams in `sync`: their plans are reviewed by a person.
- Forges other than GitLab and GitHub. The forge interface admits them; none is needed now.
