## Replace, never move

Two ways bring a newer upstream release into an update whose merge request waits: move the target inside the same merge request, by merging the newer release onto its branch, or end the update and open a new merge request.

Moving the target keeps one merge request and one link, but it changes what an approval or a silent read covered. A person who read the diff and decided to merge it later leaves no trace the forge's API returns: no comment, no approval, at most a page view that only the forge's own analytics see. If the tool then merged a newer release onto the branch, the merge request would show a diff that person never read, and a merge on the strength of the earlier read would land unread code. The tool cannot tell that case from a merge request nobody opened, so moving the target would break the guarantee behind "Each target is fixed when the update starts": what a person reviewed is what lands.

Replacing the merge request keeps that guarantee. The old merge request is closed unmerged, with its diff and pipeline intact for anyone who read it, and the new one starts a review from scratch at a new target. The update's targets stay fixed for its whole life; a replacement is the end of one update and the start of another.

The cost is noise: a closed merge request per replacement, and two events for watchers of the project and for integrations subscribed to merge request events. A minimum age, `replace_after`, bounds it by the review rhythm the fork's owner chooses rather than by the upstream's release rhythm, and several releases published during that time collapse into one replacement at the newest. The setting is off by default, because the noise is a choice of the fork's owner.

## Only releases trigger a replacement

An upstream without `tags` moves on with every commit to its branch. A replacement on every move would replace the merge request each time `replace_after` elapses, which is what a minimum age is meant to avoid, and would never let a busy branch's update settle. A release is the upstream's own signal that a point is worth taking, so only an upstream with `tags` triggers a replacement, and the configuration refuses `replace_after` where no upstream has `tags`, since the setting would do nothing.

A release here is what the upstream's newest-release rules admit as a target, the same tags every other part of `sync` takes. With `prereleases = true` the fork's owner already chose prerelease tags as targets, so a newer prerelease triggers a replacement, and a sync merge naming a prerelease tag is the tool's own choice, not a revision a person picked; a narrower rule here would keep merge requests open on targets the owner asked to move past.

When a release triggers a replacement, the new update is planned as an update without an open merge request would be, with the targets an update about to start takes: `max_conflicts` picks the newest tag within the limit, as `start` and `sync` do, and an upstream without `tags` is taken at its fetched tip. The replacement is a new update in every respect, so it takes what a new update would take, and the limit that keeps an update's conflicts resolvable in a day applies to it as well. A replacement whose merges conflict anyway replaces nothing, as below.

## What counts as untouched

The decision rests on the merge request's branch and on signals the forge returns through its API, read again just before it is closed:

- The branch: every commit on the head's update line is a sync merge of a `follow` upstream or a catch-up merge. A fix someone pushed and a merge by the forge's update button show a person's work or decisions, and the replacement would drop them.
- The targets: the tool's own rules chose the target of every sync merge, which its record proves with `Intake-Chosen`, and a sync merge of an upstream with `tags` names a tag its newest-release rules admit. A revision a person named with `start` is that person's choice, which the newest release must not override, even when it names the very release the rules would take: a tag in the record cannot tell the two apart, so the record says which rule chose the target, and a record without that proof, as every record of an earlier release, counts as a person's choice. That keeps the merge requests of forks that upgrade, until their next update.
- The merges themselves: the tree of every sync merge and catch-up merge of the line is the clean merge of its parents, which the tool recomputes with `git merge-tree` as `git intake conflicts` does. A merge that needed a resolution, or that someone amended with a change of their own while keeping its message and parents, holds a person's work the replacement would drop.
- Activity: no approval, no review on GitHub in any state, no requested reviewer or team, no comment other than the forge's system notes, no reaction on the merge request itself, no assignee, no draft flag, no automatic merge and, on GitLab, no `merge_after`, a time a person scheduled the merge for. An instance older than that field answers without it, which shows no schedule rather than an unreadable signal, since nobody could set one there. `sync` itself never comments, approves, assigns or marks a draft. The notes `land` writes about a pause of the merge queue are ordinary comments and count, which is intended: `land` is run to merge the merge request, and a landing is a decision to merge it. The forge cannot tell a person from an automation reliably on both forges, so a bot's comment counts as well: a project whose bots comment on every merge request gets no replacements, which is the behaviour without the setting, never a replacement of a merge request someone engaged with. Assignment and automatic merge are counted because they are how a person queues a merge request they approved without leaving a comment, and a review request and a reaction because they show that someone was asked to read it or did. A review request also comes from code owners, which the forge asks automatically: a project whose code owners cover the update's paths gets no replacements, as one whose bots comment does. GitLab reports every automatic merge, "merge when checks pass" included, as `merge_when_pipeline_succeeds`, which is what the tool reads.

A signal the token cannot read makes the merge request count as touched. The failure mode of every rule here is to keep the merge request, which is the behaviour without the setting.

The age is measured from the forge's creation time of the merge request, not from its last push: catch-ups by the tool keep a merge request current without anyone looking at it.

The checks run cheapest first: whether GitLab is merging the merge request, its age, its branch and a pause of the merge queue ask nothing of the forge; only then does the plan predict the conflicts of each newer tag under `max_conflicts`, and the reads of the activity come last. A merge request held by a cheap check costs no prediction and no read.

## A replacement never moves an upstream back

`max_conflicts` picks the newest tag within its limit from the integration tip as it stands, and a fork's own changes made since the merge request opened can push its target below the merge request's. A replacement at that tag would move the upstream back, which no update does. So for every upstream of the merge request's update, the plan's target must be the merge request's or contain it, and, for an upstream with `tags`, be a higher version; otherwise the merge request is kept. A maintenance tag on a branch the upstream later merged has a lower version and does not contain the newer release, and is refused the same way.

## Order of the replacement

A replacement merges the new update locally first, then closes the old merge request, deletes its branch, and publishes the new update. The new update needs `git-intake/update`, which the old merge request's branch holds, and the tool never force-pushes, so the old branch is deleted before the push, under a lease on the head read. Opening the new merge request first would need a second branch and leave two open update merge requests, which every other rule assumes cannot exist.

Merging first means a conflict is found before anything on the forge changes, so a conflicting release replaces nothing and the old merge request stays open and mergeable. Unlike a conflict in an ordinary `sync`, the attempt is discarded instead of being left in progress: `finish` could not publish it while the old merge request is open, so resolving it locally would lead nowhere. The run reports the conflict and exits with status 1 so that the job shows it, and the way on is to merge the old merge request or to withdraw it; either way the next update meets the conflict in the ordinary way.

Before it closes anything, `sync` reads the forge's merge settings and refuses as `finish` does, since a closed merge request whose replacement cannot be published would leave the update without one. Just before closing, it reads the merge request and the integration branch again, as it does before pushing a catch-up, so that a comment or a merge made while it merged stops the replacement: the activity first, then one listing of the publish remote with the merge request's branch, the integration branch and the record of a pause, and the merge request last, whose state, head and the traces its answer carries, such as an assignee or an automatic merge, are checked again, so that the window for a change before the close is as short as the forge allows. GitLab's `locked` state, the moment of a merge, counts as merged here.

The window cannot be closed, as a merge queue may merge between the last read and the close. So the state the forge answers to the close decides: a merge request it reports merged or being merged gets its description back and the run ends with status 0, one still open gets its description back and the run ends with status 2, and only a closed one goes on. A forge that closed it but kept its old description, which records its targets, gets the note in a second request, so that a replaced merge request never declines its targets. That request is made again in place, as the one that opens a merge request after the push, and not by running `sync` again: the next attempt would find the merge request closed and declining its targets. When it fails all the same, the run stops with status 2 and names the merge request whose description is left to replace by hand.

The replacement runs inside the retries of `sync` in merge-request mode, which repeat the whole run on a failure that may pass up to its push: a failure after the close leads the next attempt the way of a run killed after the close, below, which finds the merge request closed and declining nothing, and the request that opens the new merge request after the push is retried in place, as for any update.

## Landings and pauses

`land` carries the merge request it was started for to the integration branch, and a replacement would take that merge request away from under it. `land` itself never replaces, and while the publish remote records a pause of the merge queue, `sync` keeps the merge request without reading its activity: a pause means a landing may be under way, and reading the record costs `sync` nothing, as it already reads it to warn of one. A record that cannot be read keeps the merge request too, as it is never taken for no pause. A `land` without a queue holds no pause, so a scheduled `sync` may replace an untouched merge request while `land` waits for its pipeline; the read again just before the close stops a replacement once `land` merged, and `land` that finds its merge request closed by a replacement merges nothing, says that `sync` replaced it, ends a pause it holds, and exits with status 0, so that the next `land` takes the new merge request.

## A replaced merge request declines nothing

A merge request closed without merging declines the targets its description records, so that a person's decision not to take a release holds until the upstream moves on. A replacement is not such a decision. The close and the new description are one request to the forge, and the new description has no hidden block of targets; by the existing rule a description without readable targets declines nothing. An earlier release that reads the replaced merge request draws the same conclusion, which a new marker inside the block would not guarantee. Nothing else reads the targets of a closed merge request: the check for a rewritten branch reads open merge requests, and the check for a merge without history reads merged ones.

If a run is killed after the close, the next `sync` meets a closed merge request that declines nothing and a branch that holds its head or the new update, which the rules for an update branch without an open merge request already resolve: the first is deleted, the second gets its merge request. The merge request closed most recently carries the note, so the run that opens the new one names it, with the releases its head lacks, as the interrupted run would have.
